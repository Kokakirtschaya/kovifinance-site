# Переезд сайта kovifinance.ru на Timeweb — подробная инструкция

Пошаговый гайд «клик за кликом». Помечено:
- **[ТЫ]** — делаешь руками в панели Timeweb / Tilda / Госуслуги.
- **[Я]** — правки в коде, готовит Claude в этом репозитории.

Главное правило безопасности: **DNS переключаем в самом конце**. Пока он смотрит на
Тильду — старый сайт работает, клиенты ничего не замечают. Если новый прод сломается,
просто не переключаем DNS.

Что у нас будет на Timeweb:
1. **Домен** kovifinance.ru — регистратор Timeweb (перенос с Tilda Domains).
2. **Managed PostgreSQL** — база аккаунтов личного кабинета (152-ФЗ: данные в РФ).
3. **Cloud App** — само приложение Next.js, деплоится из GitHub по Dockerfile.

Ссылки на панель: https://timeweb.cloud/ (Cloud — Apps и БД) и
https://timeweb.com/ (домены/регистратор). Это два раздела одного аккаунта.

### Что сломано прямо сейчас

**Вход в ЛК падает с 500** на временном домене (`This page couldn't load` при отправке
формы с e-mail).

База ни при чём — проверено запросом к `/api/auth/session` с несуществующим токеном
сессии: Auth.js сходил в Postgres и вернул `null`, HTTP 200. Эндпоинты Auth.js
(`session`, `providers`, `csrf`) отвечают 200.

Значит валится отправка письма. SMTP при этом настроен правильно — `smtp.yandex.ru`,
порт `465`, `SMTP_USER` и `EMAIL_FROM` = `info@kovifinance.ru`. **Но `SMTP_PASSWORD`
в списке переменных не обнаружен** (сверка 2026-08-05). Без него `nodemailer` падает
на авторизации, исключение всплывает из server action → 500.

Проверить точный текст в панели App → вкладка **«Логи приложения»**: ожидается
`Invalid login: 535 Authentication failed` или подобное.

## Этап 1. Перенос домена kovifinance.ru: Tilda → Timeweb  **[ТЫ]**

Это перенос **регистрации** домена (не хостинга). Причина — требование идентификации
владельца через Госуслуги (в реестре домен сейчас `UNVERIFIED`); Timeweb это закрывает.

⚠️ **Особенность нашего случая (проверено 2026-07-20):** DNS домена сейчас обслуживают
**серверы Тильды** — `ns1.tildadns.com` / `ns2.tildadns.com`. Значит и запись сайта, и все
записи почты Яндекса настроены В ПАНЕЛИ ТИЛЬДЫ. Если просто увести регистратора, Тильда
может перестать отдавать DNS → сайт И почта лягут одновременно. Поэтому порядок такой:
**сначала переносим DNS на Timeweb, и только потом — регистратора.**

### 1.1. Создать DNS-зону в Timeweb и продублировать ВСЕ записи ✅ СДЕЛАНО

1. https://timeweb.cloud/ → раздел **«Домены»** (или «DNS»).
2. Добавить `kovifinance.ru` как **внешний домен** — он зарегистрирован не в Timeweb,
   нужен режим «домен у другого регистратора / только управление DNS». Если такого
   пункта в интерфейсе нет — написать в поддержку Timeweb, сценарий стандартный.
3. **Удалить автоматически созданные записи-заглушки.** Timeweb при создании зоны обычно
   заводит свои A/CNAME на парковку — если их оставить, после смены NS сайт уедет на
   заглушку Timeweb вместо Тильды.
4. Внести все записи из таблицы 1.0. На что смотреть:
   - в поле «значение» MX и CNAME — **точка в конце** (`mx.yandex.net.`), иначе панель
     достроит имя до `mx.yandex.net.kovifinance.ru`;
   - MX-приоритет `10` — отдельное поле;
   - имя хоста для DKIM — ровно `mail._domainkey` (панель сама допишет домен);
   - SPF/DKIM/DMARC вводить **без внешних кавычек** — панель добавит их сама.
5. Записать выданные Timeweb имена его NS-серверов — они показаны в свойствах зоны
   (обычно вида `ns1.timeweb.ru`, `ns2.timeweb.ru`, `ns3.timeweb.org`, `ns4.timeweb.org`,
   но брать **ровно те, что показала панель**, а не эти).

**Проверка ДО переключения** — можно спросить сервер Timeweb напрямую, он ответит из
новой зоны, хотя делегирование ещё на Тильде. Подставить свой NS из шага 5:

```bash
NS=ns1.timeweb.ru   # ← имя из панели
dig @$NS kovifinance.ru A     +noall +answer
dig @$NS www.kovifinance.ru   CNAME +noall +answer
dig @$NS kovifinance.ru MX    +noall +answer
dig @$NS kovifinance.ru TXT   +noall +answer
dig @$NS mail._domainkey.kovifinance.ru TXT +noall +answer
dig @$NS _dmarc.kovifinance.ru TXT +noall +answer
```

Ответы обязаны совпадать с таблицей 1.0 **до символа**. Пока не совпали — NS не трогать.

### 1.2. Сменить NS у домена на Timeweb (в панели Тильды) ✅ СДЕЛАНО

> **Итог 2026-08-05.** Реестр отдаёт `ns1.timeweb.ru`, `ns2.timeweb.ru`, `ns3.timeweb.org`,
> `ns4.timeweb.org` — Тильды в делегировании нет. Проверены и совпали с таблицей 1.0:
> `A @` → `176.57.65.207`, `CNAME www` → `kovifinance.ru.`, `MX` → `10 mx.yandex.net.`,
> SPF, DKIM (`mail._domainkey`), DMARC (`_dmarc`). Сайт отвечает 200, почта цела.
>
> ⚠️ В истории зоны за 4 августа видно опечатку: SPF-строка была ошибочно создана
> в `_dmarc` (`v=spf1 include:_spf.timeweb.ru`), затем удалена. Итоговое состояние верное,
> но на будущее: такие ошибки в почтовых записях проявляются не сразу.

1. Личный кабинет Tilda → **«Домены»** → `kovifinance.ru` → настройки **NS / DNS-серверы**.
2. Заменить `ns1.tildadns.com` / `ns2.tildadns.com` на NS Timeweb из шага 1.1
   (внести **все** выданные, не два из четырёх).
3. Ждать делегирование: обычно 15 мин – 4 ч, по регламенту до 24 ч.

**Как понять, что переключилось** (реестр .RU — источник истины):

```bash
whois kovifinance.ru | grep nserver     # должны быть NS Timeweb
dig NS kovifinance.ru +short            # то же, но из кеша резолвера
```

4. **Проверить, что ничего не отвалилось:**
   - `curl -sI https://kovifinance.ru | head -1` → сайт на Тильде по-прежнему отвечает;
   - `dig kovifinance.ru MX +short` → `10 mx.yandex.net.`;
   - **письмо снаружи на `info@kovifinance.ru` дошло** (с личной почты, не с домена);
   - **письмо из `info@kovifinance.ru` наружу ушло** и в заголовках получателя
     `spf=pass` и `dkim=pass` (в Gmail: «Показать оригинал»).

Пока пункт про почту не проверен — **дальше не идти**. Это единственный шаг, где можно
уронить почту, и чинится он мгновенно только пока помнишь, что менял.

**Откат:** вернуть в Тильде прежние NS `ns1.tildadns.com` / `ns2.tildadns.com`.
Зона Тильды никуда не делась, всё вернётся за то же время делегирования.

После успеха DNS больше не зависит от Тильды — можно спокойно переносить регистратора (1.3).

#### 1.3.4. Идентификация владельца через Госуслуги (ЕСИА)

Основание — **ФЗ № 569 от 29.12.2025**. С **1 сентября 2026** любые ключевые операции
с доменами `.ru`, `.рф`, `.su` возможны только после идентификации администратора:
регистрация, **продление**, смена администратора, **смена регистратора**, делегирование
и **смена NS**.

**Что это значит на практике** (уточнено 2026-08-05):

- Сайт 1 сентября **не выключается**. Ограничения касаются операций, а не работы домена.
  Жёсткий срок для нас — продление, `paid-till: 2027-01-26`.
- Идентифицируется **не домен, а администратор** — то есть аккаунт у регистратора.
  Один раз на аккаунт, на все домены сразу. При смене регистратора подтверждать заново.
- Нужна именно **«Подтверждённая» учётная запись** Госуслуг. Упрощённая и стандартная
  не годятся. ✅ Проверено: у Коки статус «Подтверждённая учётная запись».

⚠️ **Главная засада, из-за которой перенос был срочным.** По документации Timeweb
(https://timeweb.cloud/docs/domains/esia-identification) механизм идентификации
**ещё не внедрён** — «в скором времени будет внедрён в панель управления». И работать
он будет **только для доменов, зарегистрированных через Таймвэб.Домены**.

Отсюда замкнутый круг, если не успеть перенести домен до 1 сентября: чтобы сменить
регистратора, нужна идентификация; чтобы идентифицироваться в Timeweb, нужен перенос.
Именно поэтому перенос запущен 4 августа — с запасом. Сама идентификация не горит,
её можно пройти и осенью, лишь бы до продления в январе 2027.

**Порядок:** дождаться завершения переноса → дождаться, пока Timeweb выкатит механизм →
панель → раздел идентификации домена → вход через Госуслуги → автоматическая сверка
данных (несколько минут).

Перед этим сверить, что ФИО, паспортные данные и дата рождения в профиле Госуслуг
совпадают с карточкой домена у регистратора — сверка автоматическая, расхождение
её провалит.

#### 1.3.5. Дождаться и проверить

Перенос .RU идёт от нескольких часов до 5 суток. Проверка:


Признак успеха: `registrar:` больше не `TILDA-RU`, а `state:` без `UNVERIFIED`.

```bash

dig @1.1.1.1 kovifinance.ru A +short       # 176.57.65.207 (Тильда, сайт пока там)
```

#### Чего НЕ делать во время переноса

- Не менять NS и записи в зоне — любые правки в этот момент трудно отличить от сбоя переноса.
- **Не удалять домен из аккаунта Тильды и не отключать там сайт** — он продолжает
  обслуживать `kovifinance.ru` до этапа 7. Отключаем только после переезда на Cloud App.
- Не менять данные владельца одновременно с переносом.

## Этап 2. Managed PostgreSQL  **[ТЫ]** ✅ СДЕЛАНО

> **Факт на 2026-08-05.** Кластер создан, приложение подключается к нему по приватной
> сети: `postgresql://gen_user:***@192.168.0.4:5432/default_db?sslmode=require`.
>
> Расхождение с планом ниже: Timeweb создал свои `default_db` и `gen_user` вместо
> задуманных `kovi` / `kovi_app`. На работу не влияет, но знать полезно.
>
> Схема применена: `docker-entrypoint.sh` при старте контейнера гоняет
> `prisma migrate deploy`, приложение поднялось — значит миграция `20260726075612_init`
> на боевой базе есть. Косвенно подтверждено запросом к `/api/auth/session`
> с несуществующим токеном: Auth.js сходил в базу и вернул `null`, HTTP 200.
>
> Грабля с SSL (см. 2.5 ниже) **не выстрелила** — `sslmode=require` работает как есть,
> `?sslmode=no-verify` не понадобился.
>
> Инструкция ниже оставлена как справка — на случай пересоздания кластера.

Auth.js. Заявки с формы живут в CRM, главная страница к базе не обращается вообще.

⚠️ **Это платная услуга с ежемесячным списанием.** Цену смотреть на экране выбора тарифа
перед подтверждением.

#### 2.1. Создать кластер

1. https://timeweb.cloud/ → **«Базы данных»** → **«Создать»**.
2. Тип: **PostgreSQL 16**. Именно 16 — столько же в `docker-compose.yml` локально
   (`postgres:16-alpine`). Совпадение версий значит, что миграции, прогнанные на локалке,
   лягут на прод один в один.
3. Регион: **Россия** (Москва или СПб). Не Казахстан, не Нидерланды — иначе теряется
   весь смысл переезда с Vercel.
4. Тариф: **минимальный**. Нагрузка — десятки строк и редкие входы в кабинет; поднять
   тариф можно потом без пересоздания.
5. Имя кластера: `kovi-db`.
6. Бэкапы: включить автоматические, если тариф позволяет.

#### 2.2. Завести базу и пользователя

После создания открыть кластер → вкладка **«Подключение»** / «Пользователи и базы»:

- база данных: `kovi`
- пользователь: `kovi_app`, пароль — сгенерировать длинный, сохранить в менеджер паролей

Строка подключения соберётся такой:

```
postgresql://kovi_app:ПАРОЛЬ@HOST:5432/kovi?sslmode=require
```

⚠️ Если в пароле есть `@ : / ? # & %` — их надо percent-кодировать, иначе строка
распарсится неправильно. Проще сгенерировать пароль без спецсимволов.

#### 2.3. Доступ по сети

Timeweb предложит один из вариантов:

- **приватная сеть кластера** — предпочтительно: App и база общаются внутри Timeweb,
  наружу база не смотрит вообще;
- **публичный адрес + белый список IP** — тогда внести IP приложения, а на время
  проверки можно добавить свой домашний IP (`curl -s ifconfig.me`), потом убрать.

Не оставлять базу открытой в интернет без ограничений.

#### 2.4. Проверить подключение

С машины, чей IP разрешён:

```bash
psql "postgresql://kovi_app:ПАРОЛЬ@HOST:5432/kovi?sslmode=require" -c "select version();"
```

Если `psql` не установлен — через контейнер (нужен запущенный Docker Desktop):

```bash
docker run --rm postgres:16-alpine psql "postgresql://kovi_app:ПАРОЛЬ@HOST:5432/kovi?sslmode=require" -c "select version();"
```

#### 2.5. Что дальше со строкой

Она станет переменной `DATABASE_URL` в настройках App (этап 5). Схему создавать руками
не нужно: `docker-entrypoint.sh` при старте контейнера гоняет `prisma migrate deploy`.

**Мне строку показывать не обязательно** — в ней пароль от базы. Если нужна проверка
формата, пришли её с заменённым паролем.

⚠️ **Вероятная грабля — SSL.** В рантайме используется `@prisma/adapter-pg` (пул
`node-postgres`). У managed-баз сертификат часто подписан собственным CA, и `pg` при
`sslmode=require` может упасть с `self signed certificate in certificate chain`.
Лечится либо `?sslmode=no-verify` в строке, либо подсовыванием CA-сертификата Timeweb.
Вылезет это на этапе 6, на временном домене — там и починим.

⚠️ **Лимит соединений.** `PrismaPg` держит пул `pg` (по умолчанию до 10 соединений на
инстанс приложения). На минимальном тарифе `max_connections` у кластера невелик — если
позже поднимем несколько инстансов App, пул надо будет ограничить явно
(`new PrismaPg({ connectionString, max: 5 })` в `lib/prisma.ts`).

- Standalone не кладёт `public` и `.next/static` — копируются отдельными слоями,
